# Сайт ко дню рождения Ани

Слайдшоу на весь экран: фотографии всплывают под музыку, между ними появляются
строки и важные даты. Три трека играют подряд, после последнего — финальный экран
и ссылка на галерею со всеми фотографиями.

Фотографии в репозитории не лежат. Архив цепляется к релизу, а сборка сама его
распаковывает, делает веб-версии и превью и публикует всё на GitHub Pages.

## Вход по вопросу

Сайт лежит на GitHub Pages, а он отдаёт страницы всем, у кого есть ссылка —
приватных Pages нет нигде, кроме Enterprise-тарифа. Поэтому на обложке стоит
вопрос из `site.config.js` → `gate`, а в `robots.txt` — запрет индексации.

Трезво про то, что это даёт: поисковики сайт не покажут, случайный человек
дальше обложки не пройдёт. Но ответ лежит в коде страницы, и файлы фотографий
открываются по прямым ссылкам. Считай это дверью с табличкой, а не замком.
Если нужен настоящий замок — это уже другой хостинг, не Pages.

Ответ сверяется без учёта регистра, пробелов и знаков: «25.07.2014»,
«25 07 2014» и «25072014» — одно и то же. Разблокировка запоминается
в браузере, так что вопрос задаётся один раз на устройство.

## Один раз включить Pages

**Settings → Pages → Source: GitHub Actions.** Из workflow это не включается —
токену сборки такого не позволено. После этого каждый push и каждый релиз
выкатывают сайт сами.

## Как залить фотографии

1. Собери фото в архив: `.7z`, `.zip` или `.tar.gz`. Вложенные папки внутри можно.
2. **Releases → Draft a new release**, тег любой, прикрепи архив файлом, **Publish**.
3. Дальше само: сборка скачает архив, отберёт картинки и выкатит сайт.

Новый архив — новый релиз (или замени файл в существующем). Сборка каждый раз
собирает галерею заново из того, что лежит в последнем релизе.

Что отсеивается автоматически: всё мельче 25 КБ, а также папки `stickers`,
`voice_messages`, `video_files`, `round_video_messages`, `profile_pictures` —
телеграм-экспорт тащит их за собой, а в галерее они не нужны.

Одинаковые кадры сборка выбрасывает сама — сверяет содержимое файлов,
в архиве их обычно несколько.

Порядок кадров задаёт `photos/order.txt`: список имён файлов, по строке на кадр.
Он собран руками под текущий архив, чтобы лента шла по жизни — сначала вдвоём,
потом свадьба, потом сын. Всё, чего в списке нет, уезжает в конец по дате съёмки
(EXIF, а если его вычистили — дата из имени файла).

Строка может быть и шаблоном со звёздочкой — тогда место в ленте занято
заранее, а имена файлов известны позже. Так сделано для свадебных кадров:
в `order.txt` стоит `wedding*`, и любые файлы с таким именем встают
на десятый кадр, сразу после ранних.

**Если зальёшь новый архив, `order.txt` под него не подойдёт** — имена файлов
будут другие, и все кадры уедут в конец списком по имени. Тогда либо собери
файл заново, либо удали его и привяжи реплики по `at` (см. ниже).

## Что правится руками

Все тексты и даты — в `site.config.js`:

| Поле | Что это |
|---|---|
| `name` | имя на обложке |
| `birthday` | `MM-DD`, от него считается обратный отсчёт |
| `togetherSince` | `YYYY-MM-DD`, от неё — счётчик «дней вместе» |
| `intro` | надпись сверху, подзаголовок, надпись на кнопке |
| `pace` | темп показа в миллисекундах — см. ниже |
| `moments` | реплики поверх фотографий — см. ниже |
| `tracks` | песни в том порядке, в каком они играют |
| `finale` | финальный экран |

Подписи к фотографиям — необязательный `photos/captions.json`. Ключ — имя файла
внутри архива:

```json
{ "photo_12@25-07-2014.jpg": "Свадьба" }
```

Соответствие «номер файла на сайте → исходное имя» сборка кладёт в `photos/index.tsv`.

## Как реплики попадают на нужные фотографии

Лента отсортирована по дате съёмки, поэтому реплику можно привязать к моменту,
а не к номеру кадра. У каждой реплики в `moments` есть:

- `onPhoto` — имя файла или шаблон. Подпись цепляется за саму фотографию
  и не съезжает, сколько бы кадров ни добавилось до неё. Так стоит «День X»:
  `onPhoto: "wedding*"`.
- `frame` — номер кадра в ленте, считая с единицы. Порядок кадров задан
  в `photos/order.txt`, так что номер — это конкретная фотография. Сейчас
  используется именно он: «Поженились» стоит на свадебном кадре, «Родился Глеб» —
  на первом кадре из роддома, «калачиком» — там, где вы спите в обнимку.
- `after` — дата, с которой реплику пора показать: она встаёт на первый кадр,
  снятый не раньше этого дня. Работает, только если у фотографий есть даты.
  В телеграм-архиве их нет — EXIF вычищен, а в именах стоит дата выгрузки.
- `at` — доля ленты от 0 до 1, если ни номера, ни даты нет.

Первые два — жёсткие якоря: они не сдвигаются вперёд ни при каких
обстоятельствах, иначе кадры с сыном пошли бы раньше, чем про него скажут.

Реплики без `after` распределяются между якорями поровну. Если места не хватает,
отступают они, а не якоря. `momentGapMin` держит минимальный зазор, чтобы
две реплики не налезли друг на друга.

## Чтобы не показывать пустые рамки

Фотографии тянутся очередью по три штуки, на десять кадров вперёд, и кадр
не выходит, пока его картинка не пришла: лучше подождать лишнюю секунду,
чем показать пустую белую рамку. Дольше `pace.stall` лента не ждёт — если
сеть совсем плохая, кадр всё-таки выйдет.

Что ещё сделано ради этого:

- фотографии ужаты до 1200px и прогрессивного JPEG (медиана 135 КБ вместо 202,
  вся лента 12 МБ вместо 20) — карточка на экране не шире 500 точек, разницы
  не видно;
- песни обрезаны по нужным кускам и пережаты в 160 кбит/с: 8,5 МБ вместо 22;
- у плееров `preload="metadata"`, а не `auto`, иначе музыка выгребает канал
  и фотографии стоят в очереди за ней;
- следующая песня подгружается не заранее, а за восемь кадров до смены.

На канале 700 кбит/с и выше пустых кадров не остаётся совсем. На 400 кбит/с
пустыми мелькают первые два-три — там уже ничего не поделать.

## Музыка

Три трека лежат в `assets/music/` и играют кусками, а не целиком. Переключаются
они не по своему окончанию, а по номеру кадра — иначе музыка разъезжается
с лентой, потому что кадры выходят по басу и интервал каждый раз разный.

| Поле трека | Что делает |
|---|---|
| `fromFrame` | с какого кадра играет |
| `start` | с какой секунды песни начинать |
| `duration` | сколько секунд играть; кусок доиграл — эстафету сразу принимает следующая песня, по второму кругу он не идёт |

Сейчас так: Lana Del Rey — кадры 1–14 (46 секунд), ZAZ вступает сразу после
свадебных кадров и держит середину, 15–58, Beautiful Boys идёт с 59-го до конца.

Переход между песнями перекрёстный, на две секунды: плееров два, и пока
один затухает, второй уже играет — тишины между ними нет. Длительность
задаёт `pace.fade`.

`fromFrame` — не единственная причина смены песни: если кусок доиграл
раньше, чем лента дошла до нужного кадра, следующая песня вступает сразу.
Назад лента песню не отматывает.

Кнопка «вперёд» в панели перематывает не песню, а саму ленту — к кадру,
с которого начинается следующая. Иначе смысла нет: музыка привязана
к кадрам, и следующий же кадр вернул бы прежнюю песню.

Показ кончается вместе с лентой, а не с последней песней: на 94-м кадре
новые не выбрасываются, последний висит ещё пять секунд, музыка уходит
в тишину — и только потом финальный экран. Всего выходит около 5 минут.

Файлы песен не резаны, играются куски — так проще передумать. Если важен
вес страницы, песни можно обрезать физически и убрать `start`/`duration`.

## Локально

```bash
node scripts/build-gallery.mjs   # пересобрать список фото из папки photos/
python3 -m http.server 8000      # http://localhost:8000
```

Накидай пару картинок в `photos/` — они подхватятся как есть, без превью.

## Структура

```
index.html              обложка и слайдшоу
gallery.html            все фотографии сеткой
site.config.js          тексты, даты, порядок песен
assets/css/style.css    оформление
assets/js/show.js       слайдшоу, музыка, реплики
assets/js/gallery.js    сетка и лайтбокс
assets/js/photos.js     генерируется сборкой, руками не трогать
assets/music/           три трека
photos/                 в git не попадает, приезжает из релиза
scripts/                распаковка архива и сборка списка
```
